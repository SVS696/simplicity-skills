# Проверка кода на простоту

Перед передачей нетривиальной реализации, рефакторинга или результата ревью проверь код на простоту. Для опечатки, переименования переменной или тривиального изменения одной строки проверку можно пропустить. Для постановок и архитектуры используй `simplicity-spec`. Стиль текста проверяй отдельно.

## Как выбрать реализацию

1. Укажи допущения. Если у задачи несколько трактовок, покажи, как выбор меняет поведение.
2. Определи, какую текущую задачу решает код. Для каждого слоя, параметра, паттерна и зависимости найди основание в этой задаче.
3. Меняй код, комментарии и форматирование в пределах задачи.
4. Опиши результат так, чтобы его можно было проверить по входным данным и наблюдаемому выходу.

Проследи выполнение от входа до результата. При исправлении дефекта найди все места вызова изменяемой функции или использования контракта. Исправь общую причину там, где определяется правило.

Проверь варианты по порядку. Выбери первый, который выполняет требования.

1. Существующее поведение уже решает задачу.
2. Подходит функция, тип или приём из проекта.
3. Подходит стандартная библиотека.
4. Достаточно встроенной возможности платформы, среды выполнения, браузера или БД.
5. Подходит установленная зависимость без дополнительной обёртки.
6. Достаточно прямого изменения в существующем коде.
7. Нужна новая реализация. Ограничь её текущей задачей.

При равной длине выбери вариант, который надёжно обрабатывает возможные граничные случаи.

## Порядок проверки

1. Зафиксируй запрос, вход, выход и критерий успеха.
2. Проверь затронутый код, места вызова и существующие решения.
3. Выбери реализацию по порядку выше.
4. Сопоставь спорные элементы с признаками в таблице. Для каждого выбери решение.
5. Проверь основание для каждого усложнения. Если основания нет, предложи более простой вариант.
6. Подготовь упрощённый код с учётом решений из таблицы. При ревью покажи готовую замену.
7. Для нетривиальной логики оставь минимальную исполняемую проверку, которая выявит регрессию. Добавь проверки, которых требуют проект и риски изменения.

## Что сохранить

Сохрани проверку входных данных на границах доверия, защиту от потери данных при возможном сбое, безопасность и доступность интерфейса для людей с ограниченными возможностями. Соблюдай явно запрошенное поведение, совместимость и обязательные ограничения проекта и платформы. Сохрани обоснованную точку расширения, если уже есть несколько вариантов или изменение позднее потребует дорогой необратимой переделки. При сокращении кода сохрани возможность проверить его корректность.

## Признаки лишней сложности

| Элемент | Что проверить |
|---|---|
| Объём кода | Можно ли заменить 200 строк на 50 и сохранить требуемое поведение? |
| Абстракция с одной реализацией | Сколько реализаций у интерфейса, Strategy, Factory, Protocol или обобщённого типа? |
| Параметры на будущее | Использует ли текущий код параметры, точки подключения и настройки? |
| Защита от невозможного ввода | Могут ли текущие вызовы передать данные, для которых написана проверка, ветвление или `try/except`? |
| Языковая модель для замены текста | Достаточно ли `sed`, `grep`, `awk`, `jq` или прямого чтения и редактирования? |
| Новая команда или флаг | Можно ли описать команду в скилле или выполнить операцию одной существующей командой? |
| Фреймворк для одного вызова | Можно ли напрямую вызвать API или функцию без LangChain, оркестратора или DI-контейнера? |
| Обёртка над стандартной библиотекой | Можно ли выполнить то же действие одним вызовом библиотеки? |
| Лишние слои | Нужны ли service, repository, mapper и DTO для CRUD одной таблицы? |
| Оптимизация без замеров | Какой замер обосновывает кэш, пул, пакетную обработку или индекс? |
| Настройка для одного значения | Может ли константа заменить переменную окружения, флаг или настройку? |
| Попутный рефакторинг | Требует ли задача править соседний код, комментарии или форматирование? |
| Скрытое допущение | От какой трактовки запроса зависит результат? |
| Повторная реализация | Есть ли нужная функция в проекте или стандартной библиотеке? |
| Иерархия классов | Можно ли решить задачу функцией или композицией? |
| Сложная система типов | Сколько конкретных типов использует обобщённый код? |
| Необоснованная асинхронность | Есть ли параллельный ввод-вывод или граница процессов, для которой нужны очередь, поток или async? |
| Обработка лишнего формата | Какие варианты входа действительно поддерживает задача? |

## Основания для более сложной реализации

| Механизм | Достаточное основание |
|---|---|
| Абстракция или интерфейс | Уже есть как минимум две реальные реализации. Если возможно, дождись третьей. |
| Кэш или оптимизация | Замер подтвердил проблему производительности. |
| Дополнительный слой или репозиторий | Есть второй источник данных или явное требование к тестируемости. |
| Флаг или настройка | Значение меняется между средами или запусками. |
| Языковая модель | Требуется понять смысл или создать содержательный текст. |
| Асинхронный вызов или очередь | Нужен параллельный ввод-вывод или обмен между процессами или сервисами. |
| Обработка исключения | Сбой возможен при работе с сетью, файлом или внешней системой. |

## Команды и обработка текста

- Для механической правки Markdown, JSON и других файлов используй инструменты shell или `Read` и `Edit`. Отдельный процесс с языковой моделью оправдан только для смысловой задачи, которую трудно решить прямой правкой за разумное время.
- Добавь простую фильтрацию в то место конвейера, где применяют правило.
- Если агент может собрать нужную команду из инструментов shell по инструкции в скилле, используй этот способ. В этом случае новый флаг или команда CLI избыточны.
- Включай в код и документацию только запрошенные примеры, сценарии и режимы.

## Решения

| Решение | Действие |
|---|---|
| `KEEP` | Сохрани элемент и назови текущую потребность. |
| `SIMPLIFY` | Замени элемент более простой реализацией. Покажи, какие строки, слои или зависимости удалось убрать. |
| `REMOVE` | Удали элемент, если потребности в нём нет. |
| `DEFER` | Запиши обоснованную будущую доработку в TODO или задачу. Если известен предел текущего решения, укажи условие пересмотра и следующий механизм. |
| `ASK` | Уточни, какое поведение требуется, если изменение затрагивает поведение или допускает разные трактовки. |

Если осознанно принимаешь известный предел, оставь рядом с кодом маркер. Например, он уместен для алгоритма O(n²), общей блокировки или эвристики с известными ограничениями. Для обычного прямого кода маркер не нужен.

```text
simplicity: <потолок>; revisit: <измеримое событие>; upgrade: <следующий механизм>
```

## Результат

Пиши пояснения к коду и замечания ревью на упрощённом техническом русском (УТР). Для английского текста применяй подходы ASD-STE100 и IBM EasyEnglish. Если проект требует `humanizer` или читателю трудно понять решение, уточни порядок изложения и пояснения. После такой правки сверь изменённый текст с исходным требованием в режиме проверки `utr` или `simplified-technical-english`, если скилл доступен. Проверь вывод на обычном случае и существенном исключении. Сохрани точные имена и форматы результата.

Покажи результат каждой проведённой проверки. Если есть находки, выдай упрощённый код и таблицу. В таблице укажи проверяемый признак и основание решения. Для очевидного удаления отдельное согласование не требуется.

```markdown
## Проход на простоту

| Элемент (где) | Запах | Почему лишнее | Решение | Что вместо |
|---|---|---|---|---|
| Интерфейс `UserRepository` в `repo.py` | Одна реализация | Код работает с одним источником | REMOVE | Функции для работы с соединением |
| Команда `edit` в `cli.py:120` | Модель для замены текста | Требуется заменить строку `s00` на `Алексей` | SIMPLIFY | Команда sed или прямая правка файла |
| Настройка `retry_policy` | Одно значение | Все среды используют одинаковое значение | REMOVE | Константа |

### Дельта сложности

Убрали один класс, один слой, 40 строк и одну зависимость.
Сохранили обработку исключения при сетевом вызове. Соединение может прерваться.
Команду модели `vidscribe edit` заменили прямой правкой файла.
Линейный поиск рассчитан на 500 записей. Если p95 времени поиска превысит 100 мс, добавим индекс по ключу.
```

Если проверка не выявила лишних абстракций и слоёв, верни одну строку:

`Проход на простоту: чисто — лишних абстракций и слоёв нет.`
